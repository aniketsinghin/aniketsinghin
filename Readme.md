## Current research — Post-Quantum Security

**The problem statement is singular: harvest now, decrypt later.**

Encrypted data being exfiltrated today does not need to be broken today. An
adversary can store it and wait. When a cryptographically relevant quantum
computer arrives, RSA and elliptic-curve cryptography fall to Shor's algorithm,
and every archived ciphertext becomes plaintext — retroactively.

This inverts how security teams reason about risk. The exposure window isn't
"when quantum arrives." It's **the moment data is captured**, which for anything
with a long confidentiality lifetime — health records, financial contracts,
state secrets, identity documents, source code, biometric templates — means the
breach has already occurred and simply hasn't been read yet.

My research addresses the migration problem this creates:

- **Cryptographic discovery at enterprise scale** — most organisations cannot
  produce an inventory of where and how they use cryptography. You cannot migrate
  what you cannot enumerate.
- **Migration sequencing under constraint** — NIST finalised ML-KEM (FIPS 203),
  ML-DSA (FIPS 204), and SLH-DSA (FIPS 205) in August 2024. Standards existing
  and estates migrating are separated by years of dependency untangling.
- **Crypto-agility as an architectural property** — designing so the *next*
  transition is a configuration change rather than a decade-long programme.
- **Hybrid deployment** — running classical and post-quantum primitives in
  parallel during the window where neither can be trusted alone.

The architectural claim I'm testing: post-quantum migration is not a
cryptography problem that architecture supports. It is an architecture problem
that cryptography happens to sit inside.
